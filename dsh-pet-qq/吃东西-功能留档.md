## 2. 两个数值是什么

| 数值 | 范围 | 含义 | 自然变化 | 投喂效果 |
|---|---|---|---|---|
| `hunger` 饥饿度 | 0–100 | 越高越饿 | 每小时 **+6** | **-45** |
| `energy` 精力 | 0–100 | 越高越精神 | 每小时 **-4** | **+8** |
| `craving` 心愿食物 | 字符串 | 她最近想吃的东西 | 30 分钟过期 | 投喂时被消费 |

**关键设计：按真实经过时间衰减，不用定时器。**
读状态时用「距上次更新过了多少小时」一次性补齐，所以桥重启、机器关机、进程被杀都不会让数值错乱。这也是它能做成纯模块、零常驻定时器的原因。

**阈值（决定语气）**：
- `hunger >= 60` → 状态词「饿了」；`>= 85` → 「饿扁了」
- `energy <= 30` → 「困了」

## 3. 完整交互流程（点菜式投喂）

```
① 饥饿值掉到低点 → 她主动提「有点饿」
        ↓
② 你顺着问「想吃什么」（普通聊天，无口令）
        ↓
③ 她回复里写 [想吃:草莓蛋糕]（她挑的，不是固定台词）
        ↓
   桥：识别标记 → 记下心愿食物（30 分钟有效）→ 把标记从文字里剥掉，绝不发到 QQ
        ↓
④ 你说「给你买了 / 喂你 / 喂她」
        ↓
   桥：检测投喂口令 → hunger -45、energy +8 → 清掉心愿 → 注入旁白
        ↓
⑤ 她按自己挑的东西回应（「终于吃到了」「…还行吧」这种自然反应，不是「谢谢投喂」）
```

**注意几个设计取舍**：
- 投喂用**明确口令**，不是"你提一嘴吃饭就算"——避免误触，保护刚修好的真人感。
- 投喂后**不短路、照常调模型**，让她自然回应；不是桥回一句固定"喂好了"。
- 她写了 `[想吃:]` 但没正文时，剥完为空 → 本轮不发消息（只记心愿），符合预期。
- 冷却 60 秒，防连点刷数值；已吃饱（hunger<=5）时投喂会触发"吃不下"的旁白。

## 5. 配置项（`config.json` → `petState`）

```jsonc
"petState": {
  "enabled": true,          // 总开关。2026-11-24 01:25 起为 true；改回 false + 重启桥 = 完全不生效、聊天零影响
  "stateFile": "pet-state.json",  // 状态落盘文件（相对桥目录）
  "hungerPerHour": 6,        // 饥饿每小时上升
  "energyPerHour": 4,        // 精力每小时下降
  "feedHunger": -45,         // 投喂后饥饿变化（负数=下降）
  "feedEnergy": 8,           // 投喂后精力变化
  "feedCooldownMs": 60000,   // 投喂冷却，防连刷
  "cravingTtlMs": 1800000,   // 心愿食物有效期（30 分钟）
  "hungryAt": 60,            // >= 此值算「饿了」
  "starvingAt": 85,          // >= 此值算「饿扁了」
  "tiredAt": 30              // <= 此值算「困了」
}
```

调参手感建议：`hungerPerHour` 调小（如 3）→ 不容易饿、语气变化更少；调大（如 10）→ 一白天不聊就饿扁，养成感强但容易烦。`feedHunger` 绝对值调小（如 -25）→ 喂一顿吃不饱，要喂两次。

## 8. 已知边界 / 后续可做

- **只有两个数值**，没有好感度。好感度极易变成「刷数值」破坏真人感，暂不做。
- **桌面无动画**：桌宠 `baifan` 槽位没接，QQ 侧只体现为文字语气。
- **主动说饿依赖主动续话**：她"主动提饿"是靠 `stateHint` 在每轮注入 + 现有主动续话机制带出来，不是独立定时器；私聊主动续话关掉的话，主动提饿也会弱很多。
- **心愿食物靠标记**：她不写 `[想吃:]` 就没有心愿，投喂时走"随便喂了点"分支。这是刻意的——不猜自然语言，避免误判。
- **冷却与"吃饱"的交互**：hunger<=5 时投喂只回旁白不加数值；冷却中不重复加但照常回话。
